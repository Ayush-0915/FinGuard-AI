### Primary Verified Findings:
1. **Training Provenance Confirmed:** The active LightGBM and Isolation Forest models were trained on `HI-Small_Trans.csv` (5,078,345 transactions, 11 raw columns), which originates from the **IBM Transactions for Anti-Money Laundering** benchmark dataset (ealtman2019 / MIT-IBM Watson AI Lab), generated by IBM Research using AMLSim with a multi-bank/multi-currency post-processing converter.
2. **Baseline Metrics Recalculated:** Using the preserved confusion matrix (`TN: 194,985`, `FP: 12,898`, `FN: 91`, `TP: 351`), discrete evaluation metrics were independently re-derived: Precision is confirmed at **2.65%**, Recall at **79.41%**, and F1 at **0.0513**. Continuous curve integrals (ROC-AUC 0.8718, PR-AUC 0.0263) cannot be independently recalculated because the raw 5M-row test CSV and continuous prediction vector were not committed to Git.
3. **Severe Lookahead Data Leakage in Original Training:** In `notebook.ipynb` (cells 21–24), lifetime account aggregates (`sender_features`, `receiver_features`) and velocity (`seconds_since_previous`) were computed across the **entire 5.08M rows** prior to the chronological split (cell 27). Training samples were therefore exposed to future transactions from the validation and test periods.
4. **Native AMLSim Schema vs Converted Kaggle Schema:** Native IBM AMLSim output produces `step, from, to, amount, type, is_sar, alert_id`. It does **not** natively produce `From Bank`, `To Bank`, `Receiving Currency`, `Payment Currency`, or FX conversion amounts. When evaluated on native single-currency AMLSim data, **8 of the 26 features become completely degenerate or constant**.
5. **No Production Modifications:** Zero production artifacts, Supabase tables, or runtime endpoints were altered.

## 2. AMLSim Outputs Verification & Schema Disambiguation

There is a distinction between **Native IBM AMLSim**, the **Kaggle IBM AML Benchmark Dataset**, and **PaySim**:

```text
+---------------------------------------------------------------------------------------------------+
| 1. PaySim (Lopez-Rojas et al., 2016) [DIFFERENT SIMULATOR - NOT AMLSIM]                           |
|    step, type, amount, nameOrig, oldbalanceOrg, newbalanceOrig, nameDest, oldbalanceDest,         |
|    newbalanceDest, isFraud, isFlaggedFraud                                                        |
+---------------------------------------------------------------------------------------------------+
                                                  vs
+---------------------------------------------------------------------------------------------------+
| 2. Native IBM AMLSim Simulator (IBM Research open-source Java/Python agent engine)               |
|    transactions.csv: step, from, to, amount, type, is_sar, alert_id                               |
|    accounts.csv:     ACCOUNT_ID, CUSTOMER_ID, INIT_BALANCE, COUNTRY, ACCOUNT_TYPE, IS_SAR, MODEL_ID|
|    alerts.csv:       ALERT_ID, SAR_TYPE, SCHEDULE_ID, START_STEP, END_STEP                        |
+---------------------------------------------------------------------------------------------------+
                                                  vs
+---------------------------------------------------------------------------------------------------+
| 3. Converted/Augmented Kaggle Benchmark Dataset ("HI-Small_Trans.csv" used by FinGuard AI)        |
|    Timestamp, From Bank, Account, To Bank, Account.1, Amount Received, Receiving Currency,        |
|    Amount Paid, Payment Currency, Payment Format, Is Laundering                                   |
+---------------------------------------------------------------------------------------------------+
```

### Verified Schema Differences:
1. **PaySim fields (`nameOrig`, `nameDest`, `isFraud`, `oldbalanceOrg`) DO NOT exist** in either native AMLSim or the Kaggle AML dataset.
2. **Native AMLSim:**
   - Single simulation clock (`step`, an integer simulation day or hour).
   - Single currency unit (all amounts in base currency).
   - Single-bank by default (sender is `from`, receiver is `to`).
   - Labels are `is_sar` (boolean/int) and `alert_id` (alert pattern ID).
3. **Kaggle Augmented Dataset (`HI-Small_Trans.csv`):**
   - Introduces multi-bank routing (`From Bank`, `To Bank`).
   - Introduces multi-currency pairs (`Receiving Currency`, `Payment Currency`, e.g. USD, EUR, INR).
   - Renames accounts to `Account` (sender) and `Account.1` (receiver).
   - Renames label to `Is Laundering`.

## 4. Leakage Investigation & Anti-Leakage Constraints

### 4.1 Temporal / Lookahead Leakage Mechanics
In `notebook.ipynb`:
```python
# Cell 21 (Full Dataset Computation BEFORE Split)
sender_features = df.groupby("sender_account").agg(
    sender_transaction_count=("sender_account", "size"),
    sender_total_amount=("amount_paid", "sum"),
    ...
)
```
- **The Defect:** When transaction $i$ occurs at Day 1, its feature vector contains the sender's total transaction count and total volume across all 10 days of the dataset.
- **Consequence:** In the training set, accounts that engage in high-volume laundering bursts on Day 9 or 10 already have massive `sender_transaction_count` and `sender_total_amount` values attached to their early benign transactions on Day 1. The decision trees split on these inflated lifetime numbers, creating an illusion of high recall while inflating false positives in production.

### 4.2 Strict Exclusion of Target-Derived Fields
The following fields must be excluded from feature vectors:
1. `is_laundering`, `is_sar`, `isFraud` (Ground-truth target labels).
2. `alert_id`, `alertID` (AMLSim metadata indicating the exact simulated money-laundering pattern instance).
3. `sar_type` (e.g., `cycle`, `fan_in`, `fan_out`, `bipartite` - defines the crime topology).
4. `accounts.csv: IS_SAR` (Oracle flag declaring whether an account is corrupt).
5. Post-transaction operational indicators (`status == 'BLOCKED'`, `investigation_id`, analyst notes).

## 5. Proposed Evaluation Protocol

To benchmark the existing baseline model against a leakage-free, AMLSim-trained experimental model without altering production systems:

### 5.1 Chronological & Graph-Safe Splitting
1. **Temporal Split Windows:**
   - **Training Set (70%):** Simulation steps $t \in [0, T_1)$.
   - **Validation Set (15%):** Simulation steps $t \in [T_1, T_2)$.
   - **Held-Out Test Set (15%):** Simulation steps $t \in [T_2, T_{\text{end}}]$.
2. **Typology Leakage Mitigation:**
   - In AMLSim, a laundering pattern can span multiple steps (e.g. fan-in at $t=10$, cycle transfer at $t=12$, fan-out cash withdrawal at $t=14$).
   - If split strictly by time, the beginning of an alert appears in train and the tail appears in test.
   - **Mitigation:**
     - Raw Account IDs (`from`, `to`) must **never** be passed as model features.
     - Features must only capture topological dynamics (velocity, degrees, amounts, channel ratios).
     - Evaluation will report metrics both on the full test set and on *unseen account subgraphs* to verify true structural generalization.

### 5.2 Phase A: Baseline Zero-Shot Evaluation (Existing Model)
- Run `models/muleguard_lightgbm.pkl` and `models/muleguard_isolation_forest.pkl` on the held-out AMLSim test set without retraining.
- Features constructed strictly using the 26-feature contract:
  - Unavailable FX features (`amount_diff`, `amount_ratio`, `currency_match`, `from_bank`, `to_bank`, `receiving_currency`, `payment_currency`) mapped to their neutral values (`0.0`, `1.0`, `1`, `1`, `1`, `"US Dollar"`, `"US Dollar"`).
- Record zero-shot Precision, Recall, F1, PR-AUC, and False Positive count.

### 5.3 Phase B: Leakage-Safe Feature Engineering Pipeline
- Calculate historical behavioral features using an **expanding point-in-time window**:
  $$\text{Count}(A, t) = \sum_{k: \text{sender}=A, t_k < t} 1$$
- Features at time $t$ use strictly $t_k < t$ (strictly preceding events).
- Categorical features encoded using only categories observed in the training split.

### 5.4 Phase C: Retrained Experimental Pipeline
- **LightGBM:**
  - Objective: `binary`.
  - Metric: `average_precision` (PR-AUC).
  - Class Imbalance Handling: Tune `scale_pos_weight` across grid `[1.0, 5.0, 10.0, 50.0, sqrt(N_neg/N_pos)]` instead of raw ratio `1231.8` to suppress false positive explosion.
  - Early stopping: 50 rounds evaluated on the validation split.
- **Isolation Forest:**
  - Trained independently on normal transactions ($y=0$) from the training partition only.
  - Evaluated via anomaly ranking: score $s = -\text{decision\_function}(X)$.

### 5.5 Metric Suite & Threshold Sweep
For both models on the held-out test partition:
- **Primary Metrics:** PR-AUC (Average Precision), Precision, Recall, F1-Score, ROC-AUC.
- **Operational Metrics:** Confusion Matrix ($TP, FP, FN, TN$), False Positive Count, False Positive Rate (FPR).
- **Threshold Calibration:** Full sweep $\theta \in [0.01, 0.99]$ in steps of $0.02$. Record standard threshold ($\theta = 0.50$) and maximum-F1 threshold ($\theta^*$).
